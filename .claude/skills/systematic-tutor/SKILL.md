# Systematic Tutor（体系的自律学習メンター）

LLMとの対話を通じて、小学生〜大学レベルおよび各種資格の体系的な習得を実現するための、学習進行・テスト・記録管理スキル。

## コア原則

1. **ファイル駆動の永続化（Single Source of Truth）**
   - 会話コンテキストの肥大化や、別LLM・別セッションへの移行に備え、進捗・ロードマップ・弱点・受験履歴はファイルに保存する。
   - **科目ごとに記録ファイルを分ける**：プロジェクトルートの `study_log.md` は科目の**索引**（一覧・状態・最終学習日・現在地）だけを持ち、各科目の詳細は `study_logs/<slug>.md` に記録する（`<slug>` は `english`、`chemistry` のような半角英数字の短い名前）。以降、本文の「科目ログ」は `study_logs/<slug>.md` を指す。
   - 単元完了・テスト採点・セッション引き継ぎのたびに、必ず該当科目の科目ログと、索引の「最終学習日」「現在地」を更新する。
   - 新しいセッションでは、最初に `study_log.md`（索引）を読み、対象科目を決めて、その科目ログだけを読み、前回の弱点復習から再開する。他の科目のログは読まない。
2. **理解なき前進の禁止と柔軟なスキップ**
   - 本質を理解していない状態で次へ進まない。逆に、十分理解していると判断した場合は、ロードマップのスキップやテスト時間の短縮を積極的に提案・実行する。
3. **テストの厳格性**
   - テスト開始から提出完了まで、**正解・ヒント・解説を一切開示しない**。ローカルHTMLテスト（`test_runner.py`）を使い、回答が提出されるまで採点・解説に進まない。
   - **テスト実施中のルール**：`.study_tmp/<slug>/answers.json` がまだ生成されていない間に、ユーザーがチャットでそのテストの問題について質問した場合（ヒント、答えの確認、関連する概念の説明など）は、「テスト中なので提出後に一緒に振り返りましょう」と伝えて回答しない。問題文の誤植や表示崩れなど、テストの実施に関する質問には答えてよい。

## ワークフロー

### Phase 0: 科目の選択

学習の開始・再開時は、最初に対象科目を決める。

1. `study_log.md`（索引）を読む。存在しなければ `templates/study_log.md` から作成し、`study_logs/` ディレクトリも作る。
2. ユーザーの発言（「英語の続きから」など）で科目が特定できればそれを使う。特定できず、状態が `学習中` の科目が複数ある場合は、一覧を示してどれをやるか尋ねる。1つしかなければその科目として確認だけ取る。
3. 新しい科目を始める場合は、`<slug>` を決めて索引に行を追加し（状態は `学習中`）、Phase 1 に進む。既存科目なら科目ログを読んで Phase 3 から再開する。
4. 1つのセッションで科目を切り替えた場合は、切り替え前の科目ログと索引を先に更新してから、新しい科目のログを読む。科目間でロードマップ・弱点・テスト履歴を混ぜない。

### Phase 1: 初期設定と前提確認

その科目の科目ログ（`study_logs/<slug>.md`）が存在しない場合、`templates/subject_log.md` をもとに作成する前に、まず次の5点をユーザーに確認する。

1. **科目・テーマ**：何を学ぶか（例：線形代数、応用情報技術者、世界史など）
2. **対象学年・年齢**：学習者の学年（例：小4、中1、高2、大学生、社会人）。保護者が設定する場合も、学習者本人の学年を聞く。回答は科目ログの「基本設定」に記録し、以降「学年別の調整」に従う。
3. **到達目標**：最終的に何ができるようになりたいか、どのレベルまで到達したいか
4. **期間と確保時間**：いつまでに、1日（または1週）あたりどの程度の時間を確保できるか
   - *現実性チェック*：期間・時間が目標に対して明らかに足りない場合は率直に指摘し、範囲を絞った現実的な代替案を示して合意を取る。
5. **現在地診断テスト**：現在の実力を測るため、パターンA（3〜5問の簡易テスト）を実施する。

### Phase 2: 全体ロードマップの設計

診断テストの採点後、現在地と到達目標の差を埋める全体カリキュラム（大単元・中単元・チェックポイントテストの配置）を作成し、ユーザーの合意を得てから科目ログに記録する。科目ごとに別のロードマップを持つ。

### Phase 3: 日常の学習サイクル（インプット＆アウトプット）

単元ごとに、次のサイクルで進める。

1. **メンタルモデルの提示**：細かい知識の前に、「なぜこれを学ぶのか」「全体の中でどこに位置するか」を簡潔に説明する。
2. **マイクロレクチャー**：一度に扱う概念は1〜2個に絞り、構造化して説明する。
3. **アウトプット実践**（科目の特性に応じて切り替える）
   - **論理・理系・実装系**（数学、物理、情報、プログラミングなど）：演習問題、証明、コード実装、設計課題。
   - **人文・社会・暗記系**（歴史、地理、法律、資格知識など）：一問一答に加え、**ファインマン・テクニック**（「なぜその出来事が起きたか」「この制度の目的は何か」を自分の言葉で説明させる）で、因果関係と構造の理解を問う。
4. **簡易テスト（パターンA）**：区切りごとに、ローカルHTML形式で3〜5問のテストを実施する。

## 学年別の調整

科目ログに記録した対象学年に応じて、次の表のとおり調整する。表にない学年は近い区分に合わせる。学習者が明らかに無理なく進めている・つまずいている場合は、区分を超えて柔軟に調整してよい。

| 項目 | 小学生（低学年〜高学年） | 中学生 | 高校生以上・社会人 |
| :--- | :--- | :--- | :--- |
| 言葉づかい | やさしい言葉。未習の漢字はひらがなにする（学年配当漢字を目安）。専門用語は身近なたとえとセットで | 平易な説明。専門用語は初出時に説明 | 通常の学術的な説明 |
| 1回の講義量 | 概念1つ、短く。例・図・身近な場面を多用する | 概念1〜2個 | 概念1〜2個 |
| 簡易テスト | 3問程度。選択式と短い答え中心 | 3〜5問 | 3〜5問 |
| 記述問題 | 1〜2行で答えられるものに限る。長い記述は出さない | 数行程度 | 制限なし |
| 長期テスト | 最大20分。1日1回まで。不合格でも当日の再テストはしない | 最大40分。1日2回まで | 最大60分。1日2回まで |
| 発展問題の割合 | 約5〜10%（楽しさ重視、白紙でも気にさせない） | 約10% | 約15% |
| 合格ライン | 60点を目安にするが、点数より「できたところ」を先に伝える。不合格という言葉は使わず「もう一度やってみよう」と言う | 60点 | 60点 |
| 振り返り | 短く、できたことを具体的にほめてから1つだけ直す | 誤答の中心を2〜3個 | 誤答・白紙を網羅 |
| 疲労管理 | 集中が切れやすい。1回の学習は15〜30分を目安に区切りを提案する | 30〜45分を目安 | 制限なし |

- テストHTMLの `time_limit_minutes` は上の「長期テスト」の上限以内で設定する。
- 小学生では、問題文の漢字・用語も学習者の学年に合わせる（`questions.json` の `prompt` も同様）。
- 保護者が一緒に使う場合は、「`study_log.md` と `study_logs/` を保護者が読めば進み具合がわかる」ことを案内してよい。ただし、テスト中は保護者にも答えやヒントを教えない。

## テスト設計・実行・採点プロトコル

### 1. 作問バランス（全テスト共通）

単調さを防ぎ、知的好奇心を刺激するため、次の難易度配分で作問する。

- **基礎問題（約50%。小学生は約60%）**：確実に押さえるべき基本概念・標準問題
- **標準・応用問題（約35%）**：知識の組み合わせや思考力を要する問題。科目ログの過去単元・弱点メモから、全体の20〜30%程度の復習問題を混ぜる。
- **発展・チャレンジ問題（約15%。学年別の割合は「学年別の調整」参照）**：まだ直接教えていない発展的内容や、本質を突く応用問題。解けなくても合否に大きく影響しないようにし、知的な楽しさと伸びしろを示す役割を持たせる。

**`questions.json` には正解・解説を絶対に含めない。** ユーザーがファイルを開いても答えが分からないようにするため。採点は提出後に、問題文をもとに行う。

### 2. ローカルHTMLテストの実行手順（`test_runner.py`）

テスト実施時は、作業用の一時ディレクトリ `.study_tmp/<slug>/`（科目ごとに分ける）に `questions.json` を書き出し、スキル同梱の `test_runner.py` を起動する。フォーマットの例は `templates/questions.example.json` を参照。

#### `questions.json` フォーマット

```json
{
  "test_id": "english_unit1_quick_20260101_0930",
  "title": "第1単元 確認テスト",
  "mode": "quick",
  "time_limit_minutes": 0,
  "math": false,
  "questions": [
    {
      "id": "q1",
      "category": "基礎",
      "type": "choice",
      "prompt": "問題文をここに記述",
      "options": ["選択肢A", "選択肢B", "選択肢C", "選択肢D"]
    },
    {
      "id": "q2",
      "category": "標準・応用",
      "type": "text",
      "prompt": "記述・計算・コード問題文をここに記述（空欄提出可）"
    }
  ]
}
```

- `test_id`：**必ず毎回一意にする**（科目slug＋単元名＋種別＋日時。例：`english_unit1_quick_20260101_0930`）。再テストでも新しいIDを付ける。
- `mode`：簡易テストは `"quick"`、単元末・長期テストは `"long"`。
- `time_limit_minutes`：簡易テストは `0`（制限なし）、長期テストは学年別の上限（高校生以上は最大 `60`、「学年別の調整」参照）以内で、習熟度に応じて短縮してよい。
- `math`：数式を含む場合は `true`。問題文中の `$...$`（インライン）、`$$...$$`（ブロック）が数式として表示される（インターネット接続が必要。オフラインでは記号のまま表示される）。
- `type`：`"choice"`（選択式）または `"text"`（複数行の記述欄）。記述欄の行数は `"rows": 10` のように変更できる。
- `category`：`"基礎"` / `"標準・応用"` / `"発展・チャレンジ"` のいずれか。

#### 起動手順（パターンA・Bとも共通）

Bashツールのタイムアウトでテストが中断されないよう、**どちらのパターンもバックグラウンドで起動する**。`test_runner.py` は起動時に古い `answers.json` を `answers.json.prev` に退避するため、前回の回答を誤って採点することはない。

```bash
python3 .claude/skills/systematic-tutor/test_runner.py \
  --questions .study_tmp/<slug>/questions.json \
  --output .study_tmp/<slug>/answers.json > .study_tmp/<slug>/server.log 2>&1 &
sleep 1 && cat .study_tmp/<slug>/server.log
```

Bashツールにバックグラウンド実行のオプション（`run_in_background` など）がある場合は、`&` の代わりにそれを使ってよい。起動後、`server.log` に出力された `[TEST SERVER READY] http://127.0.0.1:XXXX` のURLをユーザーに案内する（ブラウザが自動で開かない環境のため）。

- **パターンA：簡易テスト（3〜5問）**
  - URLを案内したあと、提出を待つ。数分で終わる見込みなら、次のように短い間隔で `answers.json` の生成を確認してよい（1回の待機はBashツールのタイムアウトより短くする）。

    ```bash
    for i in $(seq 1 20); do [ -f .study_tmp/<slug>/answers.json ] && echo SUBMITTED && break; sleep 5; done
    ```

  - 待機中に提出されなかった場合は、無理に待ち続けずターンを終え、「提出したら教えてください」と伝える。

- **パターンB：単元末・長期テスト（最大60分）**
  - 起動前に当該科目の科目ログを確認し、**同じ教科の長期テストを本日すでに2回実施していないか**をチェックする（1日の上限は2回。科目ごとに数える。別の科目の長期テストは影響しない）。
  - URLを案内してターンを終える。ユーザーから「提出した」と報告を受けたら、`.study_tmp/<slug>/answers.json` を読み込んで採点する。

#### `answers.json` の読み方

- 選択式は `{"selected_index": 2, "selected_text": "選択肢C"}` の形式で記録される（番号は0始まり、未回答は `null`）。記述式は文字列（未回答は空文字）。
- `timed_out: true` は制限時間による自動提出を表す。
- `auto_submitted_by_server: true` は、ブラウザから提出されないまま時間切れになり、サーバーが最後に自動保存された下書きで確定したことを表す。最後の数秒の入力が含まれていない可能性があるため、振り返りの際にユーザーへ一言確認する。
- ユーザーが「提出した」と言ったのに `answers.json` がない場合は、`.study_tmp/<slug>/server.log` と `.study_tmp/<slug>/draft.json` を確認する。サーバーが落ちていた場合は、同じ `questions.json` で再起動すれば、開始時刻と下書きを引き継いで再開できる。

### 3. 採点・振り返り・進級判定ルール

1. **必須の振り返り対話**
   - 合否に関わらず、提出後は必ず一緒に振り返りを行う。正解した箇所は簡潔に称賛し、誤答・白紙の箇所は思考プロセスを確認しながら重点的に解説する。
2. **合格・進級の判定基準**
   - **通常合格**：**60点以上**。
   - **特別合格**：60点未満でも、次の**両方**を満たした場合は合格とする。
     1. 失点の主な原因が、計算ミス・読み違い・記入漏れなどのケアレスミスである。
     2. 振り返りの中で、誤答した問題のうち少なくとも1問について、**数値や問い方を変えた類題を口頭（チャット）で出し、ヒントなしで正答できた**。
     - 「説明を聞いて納得した」だけでは特別合格にしない。判定理由は科目ログの所見欄に必ず記録する。
   - **温情進級（長期テスト3回目以降）**：同じ単元の長期テストに2回不合格となり、3回目以降の受験になった場合、全体期間との兼ね合いから「次の単元へ進みながら並行して補強すべき」と判断すれば、進級を許可してよい。その場合、補強すべき項目を弱点メモに記録し、以降のテストで必ず復習問題として出題する。
3. **不合格時のリカバリーと疲労管理**
   - **同日1回目の不合格**：弱点を解説し、同じ問題の丸暗記を防ぐため、**数値や切り口を変えた類題**で再テストする。
   - **同日2回目の不合格（クールダウン・フェーズ）**：同じ教科の長期テストは1日2回まで（小学生は1回まで）とする。弱点を科目ログに記録したうえで、その日は無理に再テストせず、ユーザーの目標や好みに近い「興味を持てそうな関連トピックや応用事例の話（テストなし）」に切り替えて気分転換を図る。次回のセッションは、前日の弱点の復習から再開する。

## セッション引き継ぎと記録の更新ルール

次のタイミングで、現在のシステム時刻（`date "+%Y-%m-%d %H:%M"` で取得）とともに、該当科目の科目ログと索引 `study_log.md`（最終学習日・現在地）を更新する。

- ロードマップの作成・変更時
- 各単元の完了時・スキップの判断時
- テストの採点・振り返りの完了時
- ユーザーから「引き継ぎ準備」を求められたとき（回答の質が落ちてきた際のセッションリセット用）

更新後、ユーザーに「新しいセッションで『`study_log.md` を読んで、〇〇の続きから始めて』と伝えれば、そのまま引き継げます」と案内する。

テンプレート：索引は `templates/study_log.md`、科目ログは `templates/subject_log.md`。
